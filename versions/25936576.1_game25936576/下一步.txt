### 实机取证（游戏运行时只读读取，已定位到根因）

用只读探针读了运行中的游戏（PID 38664，build 25936576），`SoldierState.status = -7`、
`action = 1` —— 也就是说请求被修改器自己的前置校验拦住了，**根本没有调用游戏函数**。
逐项复现旧代码的校验链，结果如下（旧 DLL 9c5112e7，4608 字节）：

| 旧校验 | 实测 |
| --- | --- |
| `typed(events, 76111160)`：events klass == `*(base+0x4895D38)` | 相等（0x2335185c050）✓ |
| `[events+0x20] == game` | 相等 ✓ |
| `[events+0xD8]`（blockGameEvents） | 0 ✓ |
| `allEvents` 列表结构 | count=344，items 长度 512 ✓ |
| `[entry+0x70] == events`（GameEvent 归属） | 344 项全部匹配 ✓ |
| 找到 `ident == 'SoldierUpgrade'` 的事件数 | 恰好 1 个（entry[69]）✓ |
| `engaged` 列表 | count=1 |

也就是说：能离线核对的项目全部通过，唯一没被排除的就是旧代码里剩下三处写死的
**类槽相等校验** —— `typed(entry, 76110384)`、`typed(holder, 76023384)`、
`typed(cluster, 76023120)`。`-7` 就出在这里。

### 补充：类槽本身是对的，-7 是「一处判不了就整条中止」

进一步用 PE 反查（扫 `.text` + `il2cpp` 段里的 `lea rcx, [rip+disp32]`，算出 RIP 相对目标，
再用 `.pdata` 定位所属函数，最后映射回方法名）逐个确认了四个槽的归属：

| 槽 | 被谁引用 | 结论 |
| --- | --- | --- |
| `0x4895D38` | `GameEvents..cctor`、`GameController.SetUpGame`、`LocalDevSimulator.Setup` | GameEvents ✓（旧代码此处正确） |
| `0x4895A30` | `BaseGameEvents.Register`、`BaseGameEvents.Serialize` | GameEvent ✓ |
| `0x4880658` | `BaseGameEvents.TryGetCluster`、`ForceFire`、以及**每一个** `GameEvents.<事件方法>` 包括 `SoldierUpgrade` | EngagedEvent ✓ |
| `0x4880550` | `BaseGameEvents.TryGetCluster`、`ForceFire`、`Setup`、`Serialize` | EngagedCluster ✓ |

同时 `EngagedEvent` 的字段确认是 0x10 ident、**0x18 cluster**、0x20 zone、0x48 tokenParams，
所以 holder→cluster 的偏移也是对的。

那么 -7 只可能来自**旧代码的写法**：它在扫描 `engaged` 列表时是「任一元素判不了就整条中止」
（`if (!typed(entry,76023384)) return -7;`、`if (!typed(cluster,76023120) || ...) return -7;`）。
只要列表里当时存在一个正在创建/正在销毁、或 cluster 指针不匹配的 EngagedEvent，整次请求就被判 -7，
哪怕 SoldierUpgrade 事件本身完全正常。用户当时正在频繁使用「战士快移」，游戏在推进，
engaged 列表本来就在不停变动，命中这种瞬时状态的概率很高。

新 DLL 已把这类扫描改成**跳过不匹配项继续找**（`continue`），不再「一处判不了就整条中止」，
并且 `engaged_before` 与 `stage` 会把当时看到的一切写进日志。

### 2026-10-15 第三轮：真正的原因找到了（ident 长度写错）

装上带诊断的新版后，用户再点一次，日志 `soldier-result_*.json` 给出：
`status = -7`、`stage = 4`（事件表里没有 SoldierUpgrade）、`hook_calls = 59`、`runs_started = 6`、
`identity_fails = 0`。**挂钩这次真的跑起来了**，identity 校验也全过，问题只剩事件查不到。

再对运行中的游戏（PID 24892）只读导出 `allEvents`，结果一目了然：

```
allEvents(0x68) count=344，owner 不匹配 0
  [69] ident='SoldierUpgrade'  len=14     ← 真实长度是 14
```

**`"SoldierUpgrade"` 是 14 个字符（Soldier 7 + Upgrade 7），而 `upgradeIdent()` 里写的是
`f<int>(text,0x10) != 13`。** 长度对不上就直接判定「不是这个事件」，于是永远找不到 →
`stage=4` → `-7`。之前 19:32 那次取证漏掉它，是因为 Python 探针直接比对字符串、没有校验长度。

修复：长度改为从字面量推导，避免再数错：

```cpp
const wchar_t expected[]=L"SoldierUpgrade";
const int length=static_cast<int>(sizeof(expected)/sizeof(wchar_t))-1;   // 14
if (!text || f<int>(text,0x10)!=length) return false;
```

新增回归用例：`native_upgrade_test.cpp` 的 scenario 3 故意把长度设成 13（旧 bug 的值），
必须被判为 NOTFOUND —— 现在这条用例就是防这个错。全套 56 项通过。

**修复后实机预演**（只读，不调用游戏函数）：事件找到 `0x1fba7135d20`、
`engaged` 列表 count=0（没有待处理升级）、`blockGameEvents=0`、zone 非空
—— 链条已能推进到调用 `HasSoldierUpgradesLeft` 与 `TryFire`。

若变成 -5 则说明该存档士兵升级科技已全部买过且不可重复（stage=11），那要另想办法。
